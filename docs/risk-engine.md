# Движок расчёта риска

## Спецификация и формулы

Реализация следует [подробной спецификации F1–F5](source-risk-model-spec.md): сила признака
вычисляется из данных, вес берётся из настроек, вклад равен их произведению.
Исходный JSON без изменений хранится в `src/test/resources/risk/data.json`: 10 клиентов,
30 услуг, 100 транзакций. Его опорное время — `2026-10-19T15:00:00Z`.

Модель `expert-f1-f5-v2`: F2 использует нехватку средств конкретной услуги после
распределения баланса по сроку продления и ID, включая услуги без автопродления; F4 усиливает сочетание
prolong_wait и нехватки денег; F5 задаёт suspended вес 15 как гипотезу команды.
Критических переопределений результата нет: вклады суммируются и ограничиваются до 100.
Score — экспертный индекс внимания, не откалиброванная вероятность оттока.

Живые услуги: `active`, `suspended`, `prolong_wait`. Для `blocked` и `deleted` оценка
`null`, уровень `NONE`; нулевая оценка живой услуги означает отсутствие баллов риска.

Для клиента, при горизонте H = 7 суток по умолчанию:

```text
дни(s)      = (expiresAt - evaluationTime) / 24 часа
доступно    = balance + (bonusState == unlocked ? bonusBalance : 0)
нужно       = сумма price живых услуг, у которых дни(s) <= H
общая нехватка = нужно > 0 ? max(0, 1 - доступно / нужно) : 0 (только сводка)
нехватка(s) = price(s) > 0 ? max(0, price(s) - fundsBefore(s)) / price(s) : 0
```

Уже истёкшие живые услуги также входят в `нужно`. `withdrawBalance`, `totalReplenished`
и транзакции в риск не входят. Все деньги — целые евроценты (`Long`): 95 означает €0.95.
Переполнение денежной суммы вызывает ошибку, а не возвращает неверное значение.

| Признак | Условие применения | Сила | Вес |
|---|---|---|---:|
| F1 | active/suspended, автопродление выключено, дни <= H | 1 - max(0, дни) / H | 50 |
| F2 | Живая услуга, дни <= H | Нехватка конкретной услуги | 40 |
| F3 | prolong_wait | 1 | 70 |
| F4 | prolong_wait, дни <= H | Нехватка конкретной услуги | 30 |
| F5 | suspended | 1 | 15 |

```text
contribution = strength × weight
rawScore     = сумма contribution услуги
score        = min(100, rawScore)
attentionScore клиента = максимум score живых услуг, иначе null
loyaltyScore = 100 - score
```

Промежуточного округления нет. Пороги по умолчанию: `LOW` при score < 40,
`MEDIUM` при 40 <= score < 70, `HIGH` при score >= 70. Округлять можно при отображении.

## Отдельный запуск на исходном наборе

Нужен JDK 25, как в настройках существующего проекта. Для генератора нужен Python 3.10+;
сторонних Python-библиотек нет. Ниже указана готовая команда для текущей машины:
JDK 25 находится во временном каталоге и передаётся Gradle явно. На другой машине
замените `RISK_JDK25` путём к своему JDK 25, например `/absolute/path/to/jdk-25/Contents/Home`.
Команды выполняются из корня репозитория, в одной оболочке:

```bash
cd /Users/artyom16/Desktop/hack-autumn-2026-api
RISK_JDK25='/tmp/codex-risk-jdk25.JniBIj/jdk-25.0.5+8/Contents/Home'
bash gradlew "-Porg.gradle.java.installations.paths=$RISK_JDK25" test riskReport --console=plain
```

Полный расчёт записывается в `build/reports/risk/fixture-risk.json`,
HTML-отчёт тестов — в `build/reports/tests/test/index.html`.
Spring и PostgreSQL для этих задач не запускаются. Время исходного набора фиксировано;
с теми же настройками результат воспроизводится.

Временный JDK исчезнет после очистки `/tmp`; в этом случае установите JDK 25
и обновите `RISK_JDK25`. Если Gradle уже обнаруживает установленный JDK 25,
можно запускать `bash gradlew test riskReport --console=plain` без свойства пути.

## Генерация и расчёт нового набора

`scripts/generate.py` — исходный генератор; его тесты — `scripts/test_generate.py`.
Пример создаёт 100 клиентов, 300 услуг и 1000 транзакций с фиксированными seed и датой:

```bash
python3 scripts/generate.py \
  --accounts 100 --services 300 --transactions 1000 --seed 7 \
  --reference 2026-10-19T15:00:00Z --out build/fixtures/demo

bash gradlew "-Porg.gradle.java.installations.paths=$RISK_JDK25" riskReport --console=plain \
  -PriskInput=build/fixtures/demo/data.json \
  -PriskAt=2026-10-19T15:00:00Z \
  -PriskOutput=build/reports/risk/demo-risk.json
```

Генератор записывает `data.json` и `002_seed.sql`. Движку нужен только JSON;
SQL автоматически никуда не загружается. При `riskInput` обязательно передайте `riskAt`
в ISO 8601 с часовым поясом: время определяет срочность и состав продлений в горизонте.
Для сравнения сценариев обычно выбирают ту же дату, что и `--reference` генератора.

`riskOutput` необязателен. Для исходного набора путь по умолчанию —
`build/reports/risk/fixture-risk.json`, для внешнего — `build/reports/risk/custom-risk.json`.
Повторный запуск перезаписывает выбранный отчёт; исходные файлы защищены от перезаписи.
Проверка генератора:

```bash
python3 -m unittest discover -s scripts -p 'test_*.py'
```

### Свои настройки

Полный пример настроек находится в `examples/risk-settings.json`.
Передайте его через `-PriskSettings=examples/risk-settings.json`, дополнив команду
`riskReport`. Для внешнего набора оставьте также `riskInput` и `riskAt`.
Можно скопировать пример в другой JSON и поменять значения:

```json
{
  "horizonDays": 7,
  "weights": {"F1": 60.0, "F2": 40.0, "F3": 70.0, "F4": 30.0, "F5": 15.0},
  "mediumThreshold": 40.0,
  "highThreshold": 70.0
}
```

Переданная карта `weights` заменяет карту весов целиком: укажите все пять признаков.
Горизонт должен быть положительным, веса — конечными числами от 0 до 100,
пороги — `0 < mediumThreshold < highThreshold <= 100`.

## Как читать JSON-отчёт

| Поле верхнего уровня | Значение |
|---|---|
| `modelVersion` | Версия формул, сейчас `expert-f1-f5-v1` |
| `evaluationTime` | Момент, относительно которого рассчитаны сроки и риск |
| `settings` | Полные настройки именно этого расчёта, включая веса и пороги |
| `services` | Результаты всех входных услуг, в том числе blocked/deleted |
| `customers` | Агрегация по всем входным клиентам |

### Услуга: признаки и оценка

`serviceId`, `ownerId` и `status` связывают результат с исходными данными.
`features` содержит все пять признаков живой услуги; у blocked/deleted список пуст.
`applicable` показывает выполнение условия применения. `strength` — сила от 0 до 1,
`weight` — вес, `contribution` — произведение силы и веса. `explanation` объясняет причину
словами, `evidence` содержит факты, использованные в расчёте.

`applicable: true` не обязательно даёт положительный вклад: у услуги 1 F2 применим,
поскольку срок близко, но денег хватает, поэтому сила и вклад равны 0.
Неприменимый признак имеет `applicable: false`, силу 0 и вклад 0.
`rawScore` показывает сумму до ограничения, `score` — результат после ограничения 100.
`null`/`NONE` означает отсутствие оценки, а `score: 0`/`LOW` — оценённую живую услугу.

У услуги 1 до окончания 30 минут, автопродление выключено:

```text
F1.strength     = 1 - (0.5 / 24) / 7 = 0.9970238095238095
F1.weight       = 50
F1.contribution = 49.851190476190474
rawScore = score = 49.851190476190474; level = MEDIUM
loyaltyScore = 50.148809523809526
renewalPrice = revenueExposure = 95 евроцентов = €0.95
```

`renewalPrice` — цена одного продления. `revenueExposure` равен этой цене, если score
достиг среднего порога и срок попадает в горизонт, включая просроченные услуги;
иначе равен 0. Это экспозиция за один период, без умножения на вероятность
и без пересчёта почасовой цены в месячную выручку.
`nextCriticalAt` — expiresAt для active/suspended или expiresAt + 5 дней для prolong_wait.
Прошедшая дата остаётся прошедшей: движок не переносит её в будущее и не обновляет статус.

`dataQualityWarnings` сообщает о противоречиях: истёкшая active/suspended, prolong_wait
дольше пяти дней, prolong_wait до срока окончания, создание позже времени расчёта.
У предупреждения есть `code` и `message`; дополнительные баллы оно не начисляет.

### Клиент: максимум и общие средства

`attentionScore` — максимум оценок живых услуг. `explanations` содержит положительные
вклады всех живых услуг по убыванию; при равенстве — по ID услуги и коду признака.
Сумма этих объяснений обычно не равна `attentionScore`: клиентская оценка берётся максимумом.

| `state` | Состав услуг клиента |
|---|---|
| `EVALUATED` | Есть живая услуга, оценка рассчитана |
| `NO_SERVICES` | Услуг вообще нет |
| `ALL_SERVICES_DELETED` | Все услуги удалены, оценки нет |
| `BLOCKED` | Живых нет и есть заблокированные; включая смесь blocked/deleted |

`liveServices` — количество живых услуг; `servicesAtRisk` — число достигших среднего порога.
`portfolioShareAtRisk` — их доля от 0 до 1, а не процент от 0 до 100.
`revenueExposure` — сумма экспозиций услуг клиента; `nearestRiskAt` — ближайшая
критическая дата услуг, достигших среднего порога, или `null`, если таких услуг нет.

`funding` содержит общие `availableFunds`, `requiredFunds`, `shortfall` в евроцентах
и безразмерную `shortageStrength` для сводки. `renewals` содержит по одному продлению каждой
живой услуги в горизонте, по сроку и ID. `fundsBefore`, `covered`, `fundsAfter` показывают
остаток и покрытие на шаге; неуспешное продление денег не списывает.
Расчёт включает услуги без автопродления и не является реальным расписанием биллинга.
У каждого продления есть собственные `shortfall` и `shortageStrength`; F2/F4 используют
эту долю. Бесплатное продление получает долю 0. Услуги вне горизонта не участвуют в F2/F4.

Пример: баланс 1000, два последовательных продления по 800 евроцентов. Первое покрыто
полностью (F2 = 0), перед вторым остаётся 200: нехватка 600/800 = 0.75, F2 = 30.
Если полное продление невозможно, деньги не списываются: следующая более дешёвая
услуга может быть покрыта этим остатком. Одинаковые сроки разрешаются по возрастанию ID.
Сценарии находятся в `src/test/resources/risk/extended-scenarios.json`, проверки — в `ServiceFundingTest`.

У клиента 5 в исходном наборе доступно 28657 евроцентов, нужно 1696: F2/F4 равны 0,
каждая из трёх prolong_wait-услуг получает F3 = 70, клиентский score — 70.
Если обнулить баланс при заблокированных бонусах, каждая услуга получает
`70 + 40 + 30 = 140` до ограничения и 100 после него. Это проверено отдельным тестом
без изменения исходного JSON.

По всему исходному набору сумма `revenueExposure` клиентов — **4144 евроцента, €41.44**.
Она включает услуги с предупреждениями: предупреждения не исключают экспозицию.

## Вызов из кода и расширение

```kotlin
val result = RiskEngine().calculate(
    snapshot = snapshot,             // все клиенты, услуги и транзакции
    settings = RiskSettings(),       // веса, горизонт и пороги
    evaluationTime = snapshotTime,   // явный java.time.Instant
)
```

Движок не зависит от Spring, базы, системных часов или изменяемого состояния расчёта.
Время передаёт вызывающий код, например получая его из `Clock`.
HTTP-контроллеры, хранение результатов и настроек, сервис загрузки и планировщик — следующий этап.
Для нового признака реализуйте `RiskFeature` в `risk/feature`, зарегистрируйте его
в конструкторе движка и добавьте вес в настройки. Сила должна быть конечной и в [0, 1].
Некорректные суммы, даты, пары статуса/времени транзакций, дубли ID, нарушенные связи
и неверные настройки завершают расчёт ошибкой. Транзакции проверяются, но на score не влияют.
