# Обогащённые сценарии для обсуждения risk engine

Набор `enriched-review-scenarios.json`: **28 клиентов, 45 услуг, 6 транзакций**, сгруппированных в 25 сценариев обсуждения.
Опорное время расчёта: **2026-10-19T15:00:00Z**, горизонт для обсуждения: **7 суток**.
Балансы и цены услуг выражены в евроцентах. Единица `amount` транзакции требует уточнения по кейсу; текущий DTO ограничивает значение диапазоном 0–1000. Все email синтетические, домен `example.test`.
ID клиентов 1001–1028, услуг 2002–2046, транзакций 3001–3006 не пересекаются с исходным и extended-наборами.

JSON содержит только поля `RiskSnapshot`: `accounts`, `services`, `transactions`.
`evaluationTime` передаётся движку отдельно; добавление его в JSON изменило бы контракт входного снимка.
Набор пригоден для будущей загрузки через API после реализации соответствующего endpoint.
Перед удалением тестов для PR JSON и это описание нужно перенести из test resources в сохраняемый каталог примеров/данных, например `examples/risk/`.

Источники структуры: `RiskSnapshot.kt`, `Account.kt`, `Service.kt`, `Transaction.kt` и enum в
`src/main/kotlin/ru/medovik/hack2026/api/dto/request/risk/`.
Семантика опирается на исходный кейсовый `data.json`, `docs/risk-engine.md` и обсуждение блока 1.
Это дополнительные синтетические данные. Набор не восстанавливает бухгалтерский журнал:
`balance` — состояние снимка, сумма приложенных транзакций не обязана его объяснять.
В текущем DTO сумма транзакции ограничена диапазоном 0–1000; цены услуг могут быть больше.

## Сценарии и решения для обсуждения

В таблице ниже записаны факты и вопросы. Она не задаёт новых правил score, финансовой формулы или приоритизации.
Численные ожидаемые score намеренно отсутствуют: их следует добавлять в тесты по мере согласования блоков.

| 1024 | Противоречивые даты в допустимой схеме | Будущее createdAt, истёкшая active, prolong_wait до expiresAt: предупреждения или исключение? |
| 1025 | Ручное продление раньше автоматического | По текущей модели оба участвуют в распределении денег; предмет обсуждения, если захотим симулировать именно биллинг. |
| 1026–1028 | prolong_wait с балансом 600 / 400 / 200 | Цена 800: дефицит 25% / 50% / 75%. Вместе с 1016/1017 показывают различимость пяти степеней дефицита. |

они есть только у крайних точек. Для сравнения денежных признаков берём только сервисы и снимок баланса;
исторические транзакции пока не участвуют в текущем score.

## Приоритет следующего обсуждения

1. Как объединять F2, F3 и F4 для prolong_wait без денег? Клиенты 1017, 1026, 1027, 1028, 1016
   задают дефицит 0%, 25%, 50%, 75%, 100% при одной цене и одном сроке.
   Решение блока 2: F2 неприменим, F3+F4 = 70+30×x. Ожидания
   70/77.5/85/92.5/100 закреплены в ExposureAndWaitingTest.
2. Что означает денежная экспозиция для hour/week/month/quarter_year/half_year/year?
   Решение блока 2: платежи в горизонте считаются внутри, наружу только месячный убыток.
   Клиент 1020: 68380 центов в горизонте, 22200 центов месячного эквивалента.
   Календарные периоды в UTC; для нормализации hour/week месяц принят равным 30 суткам.
3. Сохраняем ли самостоятельный риск suspended и участие ручных продлений в очереди денег?
   Пара 1006/1007 изолирует статус, клиент 1025 — конкуренцию ручного и автоматического продления.

Проверки набора должны фиксировать форму DTO, уникальность ID, связи, точные границы времени и состав пар.
Спорные оценки фиксируются только после решения пользователя. Для ошибок импорта (дубли ID, битый enum,
неизвестный ownerId, отрицательная сумма) лучше сделать отдельные негативные payloads:
они не должны ломать целиком этот валидный снимок для демонстрации API.
