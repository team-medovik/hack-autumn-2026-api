# Генератор → PostgreSQL → Kotlin API

Потребитель реализован в ветке `feature/generator-postgres-consumer` от актуального
`develop` (`b98fb8a`). Он не вызывает ML и не меняет правила поведения генератора.

## Какие очереди существуют

- В Python — очереди **будущих действий** (`heapq`), сохранённые в checkpoint.
  Первые задачи создаются из профилей/дат клиентов, следующие — при исполнении
  действий: покупка ставит срок продления, результат оплаты вызывает реакции.
- В PostgreSQL — `generator_inbox`, очередь **уже произошедших событий**, которые
  Kotlin должен применить. Это одновременно неизменяемый журнал для аудита.

Планировщик Spring раз в секунду вызывает потребителя. Сначала тот обрабатывает
ранее сохранённую очередь, затем забирает следующую HTTP-страницу и обрабатывает её.
HTTP выполняется вне транзакции БД. Брокер сообщений и Redis для этого потока не нужны.

## Хранение и атомарность

Flyway `V6__generator_inbox.sql` создаёт две таблицы:

| Таблица | Назначение |
|---|---|
| `generator_consumers` | Привязка sourceId → runId, курсоры приёма/применения, рабочая и опубликованная проекции, время источника, retry/backoff |
| `generator_inbox` | Событие, его последовательность и отметка применения; `PRIMARY KEY(run_id,sequence)`, `UNIQUE(run_id,event_id)` |

`received_sequence` продвигается в одной транзакции с добавлением страницы в inbox.
`applied_sequence` продвигается в одной транзакции с изменением балансов/услуг и
отметками `applied_at`. При откате ничего из этих изменений не сохраняется.

Повтор той же страницы сравнивается с сохранённым содержимым, но не добавляет
новые записи. Изменившийся payload на прежней позиции, повтор eventId на другой
позиции, разрыв последовательности или несовпадение владельца — ошибка, не пропуск.
После коммита и потери подтверждения повторная обработка начинает с сохранённого
`applied_sequence`; пополнение и списание не применяются второй раз.

Обработчик получает `FOR UPDATE SKIP LOCKED` на **строку потребителя целиком**.
По одному запуску работает один обработчик; разные потоки могут обрабатываться
параллельно. Нельзя разбирать произвольные соседние события через SKIP LOCKED:
они используют общий баланс и должны сохранять исходный порядок.

При ошибке повтор откладывается в PostgreSQL: 1, 2, 4 … до 60 секунд. Событие не
помечается успешным и не отправляется автоматически в «мёртвую очередь» с пропуском.
Очередь сначала дренируется даже при недоступном генераторе. При отставании
обработчика приём ограничен, чтобы не накапливать бесконечный backlog.

## Состояние для dashboard

События собираются в `RiskSnapshot`: аккаунты, общий баланс, услуги, сроки и статусы.
Все суммы — `Long`, целые евроценты. `payment_failed` ничего не списывает.
Нефинансовые ограничения, снятие ограничений и замены остаются также в полном журнале.
В legacy `transactions` ничего не подставляется: полноценные платежи хранятся в inbox.

Рабочая проекция может быть на середине страницы/потока. Она **не выдаётся** dashboard.
Опубликованная проекция обновляется только после применения всех принятых событий,
когда источник сообщил `hasMore=false`. Она соответствует одному `asOf` и ревизии.
Пустая страница может продвинуть виртуальное время без изменения балансов.

При `APP_GENERATOR_USE_FOR_DASHBOARD=true` существующие клиентские и dashboard-ручки
читают эту проекцию. Риск рассчитывается на её виртуальный момент, а не часы сервера.
Импортированные JSON не переписываются. При выключенном флаге сохраняется прежний
источник из `billing_snapshots`. До первой публикации live-режим показывает отсутствие
данных, а не незаметно переключается на сторонний JSON.

Исторический недельный ряд live-снапшотов здесь не накапливается: dashboard получает
только текущий опубликованный снимок. Это не реализация прогнозов по неделям.
Добавлена поддержка `day` и нормализация суточной цены к 30 суткам; сам суточный тариф
по-прежнему синтетический. Остальные формулы актуального develop не изменялись.

## Настройка

В окружении Kotlin API:

```dotenv
APP_GENERATOR_ENABLED=true
APP_GENERATOR_USE_FOR_DASHBOARD=true
APP_GENERATOR_SOURCE_ID=aeza-live
APP_GENERATOR_BASE_URL=http://generator-api:8000
APP_GENERATOR_SERVICE_TOKEN=<тот же секрет, что у генератора>
APP_GENERATOR_PAGE_SIZE=100
APP_GENERATOR_APPLY_BATCH_SIZE=1000
APP_GENERATOR_POLL_DELAY_MS=1000
APP_GENERATOR_REQUEST_TIMEOUT=10s
```

По умолчанию consumer выключен. Включение live dashboard — отдельный явный флаг.
Spring Boot применяет Flyway-миграцию обычным способом. Продакшен-БД в локальных
проверках не использовалась: все проверки выполнены на отдельном PostgreSQL 16.

API уже использует Docker-сеть `backend`. Генератор подключается к той же сети:

```sh
docker compose -f ../hack-autumn-2026-ml/compose.generator.yaml \
  -f generator-network.override.yml up -d --build
```

Сеть должна существовать; её создателем остаётся окружение развёртывания.
`APP_GENERATOR_SERVICE_TOKEN` в API и `GENERATOR_SERVICE_TOKEN` в генераторе должны
совпадать. Секрет не хранить в Git. HTTP-клиент не следует перенаправлениям.

Первый успешный polling фиксирует runId в БД. При исчезновении этого запуска или
новом runId потребитель не сбрасывает курсор автоматически. Для нового независимого
запуска задайте новый `APP_GENERATOR_SOURCE_ID`; прежний журнал останется доступным в БД.

Администратор может прочитать `GET /api/v1/admin/generator/consumer`:
включённость, источник dashboard, оба курсора, опубликованную ревизию/время,
`lastError` (`FETCH_FAILED` / `APPLY_FAILED`) и время следующей попытки. Балансы,
event payload и сервисный секрет этот endpoint не раскрывает.

## Проверки

25.10.2026: **11 тестов прошли, 0 пропущено, 0 ошибок** на изолированном PostgreSQL 16
и JDK 25. Дополнительно собран и запущен настоящий Spring Boot JAR с включённым
планировщиком, живым Python worker и FastAPI в отдельных контейнерах.
Перед перезапуском бека оба курсора были 10, после — 16; `runId` сохранился,
в inbox 16 уникальных событий и 0 ожидающих, опубликованный snapshot совпал с
текущим Python snapshot. Локальный результат: `build/consumer-e2e-result.json`.

Проверены повторные страницы и повторное применение, восстановление с новой
инстанцией потребителя, конкурентная работа двух обработчиков, rollback PostgreSQL,
разрывы/изменения событий, смена runId, backoff, пустые страницы и HTTP-клиент.
Отдельные JVM-процессы проверяют продолжение очереди после рестарта, падение после
коммита до подтверждения и принудительное завершение во время транзакции.

Полные журналы Python (3 177 lifecycle-событий и 239 событий с hour/day/month)
применены повторно порциями; конечные проекции совпали с Python-снапшотами.
Это проверка корректности доставки и применения, а не качества прогнозов ML.

Тестовые исходники перед PR удаляются согласно ранее заданному процессу проекта.
Локальные XML/HTML-результаты проверок остаются в `build/test-results/test` и
`build/reports/tests/test`. Сборка выполняется на JDK 25.

## Границы гарантий

Нет повторного применения **в этой PostgreSQL-проекции**. Внешние действия (письма,
webhook, вызов ML) не входят в транзакцию: для них понадобится отдельный outbox.
История inbox не очищается автоматически; объём JSON-проекции растёт с портфелем.
Для большого объёма следует вынести аккаунты/услуги в отдельные индексируемые таблицы.
Этот блок не переносит внутренние задачи Python-движка в PostgreSQL и не делает
горизонт генератора бесконечным.
