# План развития backend Retention Radar

## 1. Цель ближайшего этапа

Собрать сквозной рабочий контур продукта:

```text
JSON-снимок
    -> валидация и сохранение
    -> расчёт риска
    -> сохранение согласованной версии результата
    -> сводка / рейтинг / карточка клиента
    -> автоматическое обновление интерфейса
```

Вычислительное ядро риска и авторизация уже существуют. Основной объём дальнейшей работы — персистентность, application layer, API чтения результатов, управление моделью, перерасчёт и эксплуатационная готовность.

## 2. Что уже реализовано

В `develop`:

- локальная авторизация: login, refresh, logout, me;
- OIDC-интеграция;
- создание пользователя администратором;
- stateless-движок расчёта риска на уровне услуги;
- агрегация риска на уровне клиента;
- объяснения вклада признаков и предупреждения качества данных;
- OpenAPI/Swagger infrastructure;
- Spring Actuator и Prometheus registry.

В отдельной ветке `feature/users-api`:

- `GET /api/v1/admin/users`;
- `POST /api/v1/admin/users`;
- `DELETE /api/v1/admin/users/{id}`;
- доступ ко всему `/api/v1/admin/**` только с ролью `ADMIN`;
- запрет удаления пользователей, которыми управляет env-конфигурация.

Поэтому отдельная новая задача на users API в roadmap не нужна. Перед завершением существующей ветки желательно закрыть критерии готовности:

- при создании генерировать временный пароль на backend или окончательно согласовать, что пароль задаёт администратор;
- если пароль генерируется, возвращать его только один раз в ответе `201 Created`, не хранить открытым текстом;
- возвращать `409 USER_ALREADY_EXISTS` для занятого email вместо общего `400 INVALID_REQUEST`;
- запретить администратору удалить самого себя;
- запретить удаление последнего активного администратора;
- добавить controller/service integration tests.

## 3. Сначала согласовать контракт алгоритма

До создания persistence и публичного API необходимо устранить расхождения между планом и текущим кодом:

1. `suspended` в продуктовом плане является контекстом, но сейчас включён в score как F5.
2. Комбинация нехватки денег и `prolong_wait` должна быть критическим правилом без двойного начисления, а сейчас вклады F2, F3 и F4 суммируются.
3. В макете есть признак соотношения бонусных и реальных денег, которого нет в текущем контракте модели.
4. Необходимо зафиксировать семантику `withdrawBalance`, бонусного баланса и коэффициента денежной потери.
5. Денежный показатель следует называть `revenueExposure` или `weightedExposure`, но не статистически ожидаемой потерей.

Коды признаков должны быть стабильными. UI не должен хранить русские названия и диапазоны самостоятельно: backend возвращает registry доступных признаков вместе с названием, описанием, допустимым диапазоном и текущим весом.

## 4. Настройки модели

Под настройками модели понимаются сохраняемые переменные, которые изменяют результат алгоритма, время его выполнения или стандартную приоритизацию клиентов. Настройки глобальны для продукта, версионируются и изменяются только администратором.

Обычный авторизованный пользователь может прочитать активные настройки, чтобы UI мог объяснить расчёт. Изменять, сбрасывать и активировать настройки может только `ADMIN`.

### 4.1 Веса признаков

Администратор задаёт вес каждого зарегистрированного признака риска:

```json
{
  "featureWeights": {
    "F1": 80.0,
    "F2": 50.0,
    "F3": 40.0
  }
}
```

Правила:

- вес находится в диапазоне `0..100`;
- `0` фактически отключает вклад признака;
- неизвестный код признака отклоняется;
- обязательный признак не может исчезнуть из запроса;
- критические комбинации хранятся отдельно от весов, чтобы не возникало двойного начисления;
- вместе с результатом расчёта сохраняются использованные веса и версия модели.

### 4.2 Пороговые значения уровней риска

Администратор задаёт границы уровней:

```json
{
  "riskThresholds": {
    "medium": 40.0,
    "high": 70.0
  }
}
```

Валидация:

```text
0 < medium < high <= 100
```

Пороги влияют на уровень клиента, фильтры, счётчики сводки и попадание услуги в финансовую экспозицию.

### 4.3 Время и периодичность расчёта

Администратор управляет четырьмя параметрами:

| Поле | Назначение |
|---|---|
| `timeMode` | `CURRENT` для реального времени или `FIXED` для демонстрации и воспроизводимого расчёта |
| `fixedAt` | ISO-8601 timestamp; обязателен только при `FIXED` |
| `horizonDays` | На сколько дней вперёд искать продления и финансовую экспозицию |
| `recalculationIntervalMinutes` | Период автоматического перерасчёта, даже если новый снимок не загружался |

Рекомендуемые ограничения:

- `horizonDays`: `1..365`;
- `recalculationIntervalMinutes`: `1..1440`;
- всё время хранится и рассчитывается в UTC;
- timezone пользователя применяется только при отображении;
- при `CURRENT` поле `fixedAt` должно быть `null`;
- при `FIXED` scheduler не обязан постоянно пересчитывать одну и ту же дату, но изменение данных или настроек всё равно запускает расчёт.

### 4.4 Финансовые параметры

Эти параметры уже предусмотрены макетом, но их окончательная семантика должна быть согласована вместе с формулой денег:

| Поле | Назначение |
|---|---|
| `includeUnlockedBonusBalance` | Учитывать разблокированные бонусы при проверке возможности продления |
| `includeWithdrawBalance` | Учитывать выводимый/реферальный баланс при покрытии продления |
| `lossCoefficient` | Коэффициент для эвристически взвешенной экспозиции |

Для `lossCoefficient` рекомендуется диапазон `0..1`. API должно одновременно возвращать максимальную `revenueExposure` и взвешенную `weightedExposure`, чтобы коэффициент не выдавался за вероятность ухода.

### 4.5 Настройки приоритизации выдачи

Приоритизация не должна незаметно менять сам risk score. Это отдельная настройка стандартного порядка клиентов в рейтинге.

Администратор задаёт упорядоченный список правил:

```json
{
  "ranking": {
    "rules": [
      { "field": "ATTENTION_SCORE", "direction": "DESC" },
      { "field": "NEXT_CRITICAL_AT", "direction": "ASC" },
      { "field": "REVENUE_EXPOSURE", "direction": "DESC" }
    ],
    "includeNoScore": true
  }
}
```

Допустимые поля MVP:

- `ATTENTION_SCORE` — сначала наиболее высокий риск;
- `NEXT_CRITICAL_AT` — сначала наиболее срочное событие;
- `REVENUE_EXPOSURE` — сначала большая денежная экспозиция;
- `TOTAL_REPLENISHED` — сначала наиболее ценный клиент;
- `CUSTOMER_ID` — стабильный технический tie-breaker.

Backend автоматически добавляет `CUSTOMER_ID ASC` последним правилом, если его нет. Поля не должны повторяться.

Настройка определяет порядок по умолчанию. Пользователь интерфейса всё равно может временно выбрать сортировку в `GET /api/v1/customers`; это не меняет глобальные настройки.

### 4.6 Контракт API настроек

```http
GET   /api/v1/model/settings
PATCH /api/v1/model/settings
POST  /api/v1/model/settings/reset
```

Права:

| Операция | EMPLOYEE | ADMIN |
|---|---:|---:|
| Просмотр | да | да |
| Изменение | нет | да |
| Сброс | нет | да |

Изменение должно использовать optimistic locking:

```http
PATCH /api/v1/model/settings
If-Match: "settings-7"
```

Успешный ответ возвращает новую версию и состояние перерасчёта. Если другой администратор уже сохранил настройки, API возвращает:

```http
409 SETTINGS_VERSION_CONFLICT
```

В ответе на конфликт нужно передать актуальную версию и время/автора изменения, чтобы UI мог предложить сохранить поверх неё или загрузить новую версию.

После успешного изменения backend:

1. валидирует весь документ настроек;
2. сохраняет новую версию;
3. запускает пересчёт по активному снимку;
4. атомарно переключает активную версию результата после успешного расчёта;
5. обновляет метрики;
6. отправляет SSE-событие клиентам.

Если снимка ещё нет, настройки сохраняются, а ответ содержит `recalculationStatus = SKIPPED_NO_SNAPSHOT`.

## 5. Целевые API

### 5.1 Обязательные API чтения

```http
GET /api/v1/analytics/summary
GET /api/v1/customers
GET /api/v1/customers/{id}
```

`GET /api/v1/customers` поддерживает:

```text
q, riskLevel, state, sort, direction, page, size
```

Ответы сводки, списка и карточки должны содержать одну и ту же `calculationRevision`, `calculatedAt`, `snapshotId` и `settingsVersion`.

### 5.2 Снимки

```http
POST /api/v1/source/snapshot/validate
PUT  /api/v1/source/snapshot
GET  /api/v1/source/snapshot
GET  /api/v1/source/snapshots
GET  /api/v1/source/snapshots/{id}
```

- `validate` проверяет структуру и ссылки, возвращает количества записей, ошибки и предупреждения, но не меняет активные данные;
- `PUT` атомарно сохраняет и активирует валидный снимок, затем запускает пересчёт;
- `GET /snapshot` скачивает текущий JSON;
- `/snapshots` предоставляет историю загрузок;
- неуспешный импорт не должен повреждать текущий активный снимок и результат.

### 5.3 Автоматическое обновление

```http
GET /api/v1/events
```

SSE-события MVP:

- `recalculation.started`;
- `recalculation.completed`;
- `recalculation.failed`;
- `snapshot.activated`;
- `settings.activated`.

Событие передаёт только идентификаторы и версии. После него frontend повторно запрашивает нужные read-endpoint’ы. Polling по `calculationRevision` остаётся fallback-механизмом.

### 5.4 Метрики и документация

```http
GET /metrics
GET /api/v1/docs
GET /api/v1/swagger
```

Минимальные Prometheus-метрики:

- количество клиентов по уровням риска;
- количество клиентов без оценки;
- `revenueExposure` в евроцентах;
- время и статус последнего перерасчёта;
- активные версии снимка, настроек и результата;
- количество ошибок валидации снимков и ошибок расчёта.

## 6. Персистентность

Для объёма хакатона достаточно хранить вход и результаты в JSONB, не нормализуя преждевременно все аккаунты, услуги и транзакции.

### `risk_snapshots`

- `id`;
- `payload JSONB`;
- `file_name`;
- `uploaded_by`;
- `uploaded_at`;
- количества accounts/services/transactions;
- статус валидации;
- признак активного снимка.

### `risk_model_settings`

- `version`;
- `payload JSONB`;
- `algorithm_version`;
- `created_by`;
- `created_at`;
- признак активной версии.

Настройки лучше хранить append-only версиями. Это даёт историю изменений, объяснимость расчёта и возможность безопасного reset.

### `risk_calculations`

- `id`/`revision`;
- `snapshot_id`;
- `settings_version`;
- `evaluation_time`;
- `status`;
- `result JSONB`;
- `started_at`, `completed_at`;
- текст технической ошибки для логов;
- признак активного результата.

Read API использует только завершённый активный результат. Пока новый расчёт выполняется, пользователю показывается предыдущая согласованная версия с признаком `recalculationInProgress`.

## 8. Общие критерии готовности

- Все изменяющие операции модели доступны только `ADMIN`.
- Все суммы передаются в евроцентах и не используют floating point.
- Время передаётся в ISO-8601 и хранится в UTC.
- Каждый результат содержит версию алгоритма, снимка и настроек.
- После рестарта сохраняются снимок, настройки и активный результат.
- Ошибка нового расчёта не уничтожает предыдущий успешный результат.
- Новая настройка или снимок появляются в UI без ручной перезагрузки.
- OpenAPI соответствует фактическим кодам ответов и DTO.
- Есть unit-тесты ядра, integration tests repositories и contract tests controllers.
- Docker Compose поднимает всё необходимое для демонстрации.

## 9. Порядок работы с Git

Каждый этап выполняется отдельной фичей:

1. обновить локальный `develop` из remote;
2. создать ветку `feature/*` от актуального `develop`;
3. работать и писать понятные сообщения коммитов на русском языке;
4. отправить ветку в remote;
5. создать PR;
6. не выполнять merge в рамках реализации.
