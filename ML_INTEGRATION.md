# ML дополняет алгоритм риска

Kotlin сначала рассчитывает обычный балл `A`, затем получает от отдельного FastAPI
вероятность потери услуги `p` и применяет согласованную поправку:

```text
delta = clamp(0.30 * (100*p - A), -20, +20)
score = clamp(A + delta, 0, 100)
```

Это продуктовый балл, а не откалиброванная вероятность. Исходные F1–F6 и rawScore
сохраняются; уровни, лояльность, экспозиция и агрегат клиента пересчитываются после
поправки. Риск клиента остаётся максимальным риском его услуг. В существующие
текстовые пояснения добавлены исходный балл, поправка и итог; отрицательные значения
в публичные factor.points не добавляются.

Для `prolong_wait` алгоритм учитывает только F3+F4, ML не вызывается. При аномалии
данных алгоритм продолжает оценивать риск и возвращать предупреждения, ML не применяется.
При неудачном продлении деньги по-прежнему не резервируются.

## Контракт и применимость

Публичные Kotlin DTO и OpenAPI не изменены. Дашборд, список клиентов, карточка,
позиция клиента и гистограмма настроек используют общий путь оценки.

Внутренний запрос — `POST /internal/v1/renewal-risk/predict`. Kotlin передаёт полный
опубликованный префикс событий до курсора снимка, runId, время прогноза, ревизию
снимка и список услуг. Обязательное имя услуги сохраняется, email исключается.
История ограничивается курсором, который публикуется атомарно со снимком.

Сервис использует тот же построитель 36 признаков, что и обучение; обе даты события
occurredAt/recordedAt должны быть не позже predictionAt. Прогноз применяется до
оплаты, в пределах 7 суток. Поддержаны `hour/day/month`; суточные тарифы синтетические.
Метка общая: услуга не продлена и не заменена подтверждённой оплаченной VPS к dueAt+5 суток.
Для часа это вероятность потери услуги за это окно, а не пропуска одного платежа.

Старая модель поддерживала только месяц из-за области обучения, а не ограничения
CatBoost. Новая обучена на всех трёх периодах; подробности и независимые результаты
находятся в ML-репозитории, `ml/ALL_TERMS_TRAINING.md`.

## Отказ ML

Таймаут, HTTP-ошибка, неверная версия, несовпадение ревизии/времени/владельца/срока,
некорректная вероятность или неполная история оставляют исходный балл алгоритма.
Отсутствующий прогноз не заменяется нулём. Ошибка отдельной услуги не отменяет
валидные прогнозы остальных. Обычный JSON-снимок без истории оценивается алгоритмом.

На время HTTP внешняя транзакция чтения приостанавливается (её JDBC-соединение
может оставаться занятым). Таймаут по умолчанию 2 секунды,
повторов нет. Валидные ответы кешируются на 30 секунд только для той же ревизии,
времени, набора услуг и версии модели; ошибки не кешируются. Максимум 64 записи.
Лимиты: 1000 запрашиваемых услуг, 100000 событий, тело 32 MiB; превышение даёт fallback.
Большие журналы потребуют следующего этапа — инкрементальных признаков/хранилища.
Вход dataset из MinIO пока явно возвращает 503: интеграция registry в эту фичу не входит.

Миграция V7 добавляет опубликованный курсор и внутренний `ml_assessment_audit`:
исходный балл, вероятность, поправку, итог, версию, настройки и причину fallback.
Аудит записывается фоновым потоком через ограниченную очередь: его задержка или
недоступность не задерживает ответ API. При переполнении/остановке запись аудита
может быть пропущена; это диагностика, не журнал биллинговых событий. События и
курсоры генератора по-прежнему сохраняются транзакционно. В логи не попадают тела
запросов и секреты.

## Включение

ML выключен по умолчанию. Сначала применить миграции API и запустить отдельный ML
контейнер с его готовым артефактом. Для общей существующей Docker-сети `backend`:

```sh
docker compose -f /path/to/hack-autumn-2026-ml/compose.ml.yaml \
  -f /path/to/hack-autumn-2026-api/ml-network.override.yml up -d --build
```

На стороне ML задать `ML_SERVICE_TOKEN`, а в окружении Kotlin:

```dotenv
APP_ML_ENABLED=true
APP_ML_BASE_URL=http://ml-service:8000
APP_ML_SERVICE_TOKEN=<тот же отдельный секрет, минимум 16 символов>
APP_ML_MODEL_VERSION=event-driven-all-terms-v1-234422ba1357
APP_ML_REQUEST_TIMEOUT=2s
APP_ML_CACHE_TTL=30s
APP_ML_MAX_HISTORY_EVENTS=100000
```

Для живой истории должен быть включён уже существующий потребитель генератора
(`APP_GENERATOR_ENABLED=true`, `APP_GENERATOR_USE_FOR_DASHBOARD=true`). ML не запускает
генератор и не изменяет его очередь, состояние или баланс. При обновлении артефакта
нужно согласованно поменять закреплённую версию в Kotlin и перезапустить ML.

## Проверка и примеры

17 Kotlin-проверок покрывают формулу, границы, агрегацию, F3+F4, аномалии, отсутствие
резервирования, PostgreSQL-историю, HTTP-контракт, восстановление после ошибок и неблокирующую
запись аудита при переполнении очереди.
Дополнительно в ML-репозитории прошли 12 inference, 9 OpenAPI и 7 проверок обучения.

Живой прогон PostgreSQL 16 → Spring Boot → FastAPI → настоящий CatBoost проверил
12 примеров (по четыре на период), совпадение вероятности с обучением до 1e-12,
публичные схемы ClientCard/DashboardResponse/ClientsResponse/ModelSettings.
Остановка ML вернула исходный балл за 0,298 с; после запуска всё восстановилось
без перезапуска API. Это локальное измерение, не нагрузочный норматив.

Все 12 результатов сохранены в [ML_INTEGRATION_EXAMPLES.md](ML_INTEGRATION_EXAMPLES.md).
Это контрастные иллюстрации, выбранные после оценки; метрики качества считаются
по всей отложенной выборке. На месячном test новая модель немного хуже старой по
Logloss/Brier; улучшение для всех периодов не заявляется. Синтетические данные
проверяют гипотезы генератора и не доказывают точность на настоящих клиентах.

По инструкции пользователя новые тестовые исходники перед PR перенесены в
игнорируемые локальные каталоги: API `build/ml-verification/test-sources`,
ML `runtime/ml-integration-test-sources`. Логи и полные ответы сохранены рядом;
в опубликованной ветке эти новые проверки автоматически не выполняются.
